# ROS 2 / Gazebo Production Gap Review and Target Architecture

**Reviewed:** 2026-09-19  
**Scope:** Review of the inherited SIH26123 build prompt, the current repository, and the architecture required for a genuinely working 10-AMR system.  
**Decision status:** This document supersedes the inherited phase list as the implementation contract. It does not claim that the target system is already implemented.

## 0. Non-negotiable product definition

This project is not a website with animated robots and it is not a conventional web backend with a simulation-shaped API.

It is a **robotics system** with a web operator console.

The complete runtime must be:

```text
operator command
  -> authenticated/idempotent gateway command
  -> ROS 2 service/action/topic
  -> scenario manager, robot agent, or JEC
  -> Nav2 action and controller
  -> Nav2 Collision Monitor
  -> velocity command
  -> Gazebo differential-drive system
  -> rigid-body physics and sensors
  -> ROS odometry, TF, scan, contacts, navigation status
  -> ROS telemetry projection
  -> WebSocket delta
  -> browser render
```

Every arrow above must exist, run, and be testable. If any arrow is replaced by a timer, random coordinate generator, hard-coded path, pre-recorded number presented as live data, or browser animation that advances the world, the product is not complete.

### What “actual working software” means here

- Gazebo performs the simulation. JavaScript and the web gateway do not.
- ROS 2 nodes are the backend. A REST service only translates operator commands and telemetry at the web boundary.
- Nav2 plans and executes motion. The fleet application does not manually increment `x`, `y`, or edge progress.
- Robot bodies have real collision geometry, inertia, footprint, velocity, and acceleration constraints.
- Sensors, odometry, TF, contacts, and `/clock` come from the running Gazebo/ROS integration.
- JEC decisions change real Nav2 execution by granting, delaying, canceling, or permitting high-level goals; JECs never publish wheel velocities.
- The frontend renders time-stamped backend state and may interpolate only between received samples.
- When ROS/Gazebo is unavailable, the UI displays `SYSTEM OFFLINE`. It does not silently start a browser simulation.
- Historical or recorded runs are available only in an explicitly labeled `REPLAY` mode.
- Metrics are calculated from ROS events, task transitions, and Gazebo contacts, not frontend counters.
- Failure controls manipulate real nodes, network paths, or Gazebo entities and report completion only after observing the effect.

### Three distinct operating modes

The UI must always display one of these modes prominently:

1. **LIVE SIMULATION** — Gazebo + ROS 2 + Nav2 are running now; commands can mutate the simulation.
2. **REPLAY** — an immutable rosbag/result run is being played through the same display contracts; controls that would mutate the run are disabled.
3. **OFFLINE** — no authoritative stream is available; the last frame may remain visible but is marked stale and never advanced.

There is no unlabeled “demo” or in-browser simulation mode.

## 1. Executive verdict

The repository contains a useful **algorithm and product prototype**, but it is not yet the ROS 2 / Gazebo AMR system described by the build prompt.

What exists today is:

- a custom Python graph / point-mass fleet simulation;
- custom robot, JEC, reservation, routing, fairness, and experiment logic;
- native Zenoh transport and an in-process deterministic experiment runtime;
- a polished Next.js dashboard that can render telemetry from that Python runtime;
- historical benchmark artifacts generated by that custom simulator.

What does not exist today is:

- a ROS 2 workspace or ROS packages;
- a Gazebo world, physics simulation, robot models, sensors, or contact data;
- Nav2 stacks, lifecycle management, costmaps, localization, actions, or velocity control;
- `ros_gz` integration;
- typed ROS coordination messages;
- a real adapter from coordination decisions to Nav2 actions;
- dynamic robot model spawning and geometry-aware admission;
- a frontend whose authoritative state comes from the ROS/Gazebo world;
- reproducible ROS/Gazebo installation and CI;
- safety evidence from physics-based runs.

The correct engineering move is **not to throw away the current prototype**. Preserve it as the fast algorithmic reference and deterministic test harness, while building a new ROS/Gazebo runtime behind explicit ports. The production demo is complete only when the same coordination policy drives actual namespaced Nav2 robots in Gazebo and the browser displays only backend-derived state.

| “Tests pass” | Separate model tests, ROS node tests, launch tests, Gazebo integration tests, browser contract tests, chaos tests, and nightly statistical experiments. |
| “Docker Compose” | Provide a tested headless image for CI and a documented WSLg/native-GPU path for GUI. Do not claim GUI portability until verified. |

## 4. Recommended platform decision

Use the supported LTS pairing:

- Ubuntu 24.04 LTS;
- ROS 2 Jazzy Jalisco;
- Gazebo Harmonic;
- Nav2 Jazzy;
- `ros-jazzy-ros-gz`;
- `rmw_zenoh_cpp` on its Jazzy release;
- Python 3.12 for coordination nodes initially, C++ only where profiling proves necessary;
- Next.js for the web application;
- PostgreSQL or SQLite only for experiment metadata and operator audit, never for the motion loop.

Gazebo officially recommends Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic, and lists Jazzy/Harmonic as the recommended compatible pair. `rmw_zenoh` supports Jazzy binaries, but its normal topology uses a Zenoh router for discovery. The design must therefore say **router-assisted discovery with peer data paths**, not “universally routerless.” A router is infrastructure, but not a fleet traffic controller; existing motion safety cannot depend on it.

For this Windows workstation, the practical path is WSL2 + Ubuntu 24.04 + WSLg or a dedicated Ubuntu installation. The current machine is not ready for ROS/Gazebo development until that environment exists.

## 5. Target system architecture

```text
                                  OPERATOR PLANE
  Next.js UI ──HTTPS/WS──> Fleet Gateway ──ROS 2 commands──> Scenario Manager
      ▲                         │                                  │
      │                         └── read-only telemetry            ├─ spawn/delete entities
      │                                                            ├─ pause/step/reset world
      └──── state frames, command results, metrics, traces ─────────┘

                                  ROBOTICS PLANE

                         rmw_zenoh router (discovery / multi-host path)
                                           │
       ┌───────────────────────────────────┼──────────────────────────────────┐
       │                                   │                                  │
  /r01 namespace ... /r10             JEC lifecycle nodes              WMS task source
  ┌─────────────────────┐          ┌─────────────────────┐           ┌──────────────┐
  │ robot_agent         │<────────>│ local reservations  │           │ task announce │
  │ Nav2 planner        │  intents │ conflict cells      │           │ bid / award   │
  │ Nav2 controller     │  leases  │ local prediction    │           └──────────────┘
  │ collision_monitor   │          └─────────────────────┘
  │ localization / odom │
  │ robot_state_pub     │
  └──────────┬──────────┘
             │ cmd_vel / scan / odom / tf
             ▼
      ros_gz_bridge / Gazebo plugins
             │
             ▼
  Gazebo Harmonic world: physics, robot bodies, racks, obstacles, sensors, contacts
             │
             └── /clock is the simulation-time authority for every ROS node
```

### 5.1 Sources of truth

| State | Authority |
|---|---|
| Physics pose, contacts, simulated sensors | Gazebo |
| Robot localization and velocity used by autonomy | Namespaced ROS localization / odometry and TF |
| Navigation execution | Namespaced Nav2 action and lifecycle state |
| Robot profile and footprint | Robot Profile Registry |
| Task ownership | WMS/task allocation protocol |
| Local reservation ownership | Responsible JEC, with lease and deterministic degraded fallback |
| UI display | Fleet Gateway projection of ROS/Gazebo state |
| Experiment result | Metrics pipeline plus rosbag, version manifest, and scenario manifest |

The frontend, database, telemetry bridge, and task allocator are never allowed to generate a pose or directly command wheel velocity.

### 5.2 Process isolation and failure boundaries

For development, components may be composed where profiling supports it, but the logical failure boundaries must remain testable:

- Gazebo server is its own process.
- Each robot has an independently addressable namespace and lifecycle.
- JECs are independently killable lifecycle nodes or processes.
- The WMS/task source is separate from movement control.
- The telemetry gateway is independently killable and restartable.
- The Next.js application is independently killable and restartable.
- The Zenoh router is independently killable and restartable.

Killing the frontend or gateway must not stop safe robot execution. Killing Gazebo must stop authoritative state. Killing a JEC must invoke the documented degraded protocol. Killing the router must never be described as harmless until discovery, existing-session behavior, and reconnection have been measured.

### 5.3 End-to-end correlation

Every operator command receives a UUID `command_id`. That identifier must appear in:

- gateway audit log;
- ROS request/service/action metadata or associated trace topic;
- scenario manager / robot agent decision trace;
- Nav2 goal metadata where applicable;
- final command result;
- frontend activity feed.

This lets a reviewer select one UI action and prove which ROS nodes handled it, which physical state changed, and why it succeeded or failed.

## 7. Canonical robot profiles and automatic large-robot behavior

A single profile must drive every layer. Example:

```yaml
profile_id: large_payload_amr_v1
kinematics: differential_drive
footprint:
  polygon_m: [[0.60, 0.42], [0.60, -0.42], [-0.60, -0.42], [-0.60, 0.42]]
  safety_margin_m: 0.18
limits:
  max_linear_mps: 0.75
  max_angular_rps: 0.70
  max_accel_mps2: 0.45
physical:
  mass_kg: 210
  wheel_radius_m: 0.10
assets:
  xacro: package://amr_description/robots/large_payload_amr.urdf.xacro
  nav2_params: package://multi_robot_nav/config/large_payload_amr.yaml
render:
  color: "#C65D3A"
```

### 7.1 UI-to-world spawn state machine

When an operator selects a large robot and drops it into a junction cell:

1. UI sends `SpawnRobotCommand(profile_id, world_pose, command_id)`.
2. Gateway validates the API payload, records the command, and calls the scenario manager.
3. Scenario manager checks world bounds, static obstacles, current robot footprints, minimum clearance, namespace availability, and JEC jurisdiction.
4. If invalid, the command becomes `REJECTED` with a concrete reason such as `FOOTPRINT_DOES_NOT_FIT` or `SPAWN_REGION_OCCUPIED`.
5. If valid, the manager instantiates the profile’s Xacro/SDF and spawns the model through `ros_gz_sim` / the ROS simulation interface.
6. It launches `/rXX` robot state publisher, bridges, localization, Nav2, collision monitor, and robot agent with `use_sim_time:=true`.
7. It waits for TF, odometry, sensor, and Nav2 lifecycle health checks.
8. It publishes `RobotReady` only after the full namespace is active.
9. The JEC recomputes admissibility and reservation geometry using the new footprint.
10. The telemetry gateway emits the real robot dimensions and pose; the frontend renders that footprint and begins interpolation from backend samples.

Dragging an active robot must not teleport it. In live mode, dropping on a destination creates a navigation request. Teleport / reset is allowed only while the simulation is paused and must be visibly labeled as a simulation operation.

### 7.3 Required large-robot end-to-end demonstration

The release demo must include this exact sequence without editing configuration files between steps:

1. Start with a mixed fleet and a running Gazebo world.
2. Open the robot catalog in the browser and select `large_payload_amr_v1`.
3. Drop it into a valid staging/junction spawn region.
4. Observe the backend command transition through `VALIDATING`, `SPAWNING`, `BRINGING_UP`, and `READY`.
5. Observe a new Gazebo body and a new ROS namespace with healthy TF, odometry, sensors, Nav2, collision monitor, and agent.
6. Assign a task from the browser/WMS input.
7. Observe Nav2 move the large robot physically and the frontend mirror its real footprint and pose.
8. Send it toward a resource where two small robots normally pass.
9. Observe the JEC automatically convert the maneuver to exclusive occupancy because of footprint geometry.
10. Attempt a route or spawn that cannot fit and receive a deterministic backend rejection with the constraining resource named.
11. Remove the robot and verify that its Gazebo entity, ROS nodes, leases, tasks, TF frames, and UI object all disappear without orphan state.

Passing only the visual portion of this demonstration is a failure.

### 7.2 Geometry-aware capacity

Fixed `capacity: 1|2` is insufficient for mixed robot sizes. Each resource should retain physical geometry:

- centerline / lane polygons;
- clear width and height;
- allowed directions;
- static clearance margin;
- intersection conflict polygons;
- speed limit and stopping distance assumptions.

At request time, the JEC computes:

- whether the robot footprint plus margins fits the aisle;
- whether two specific robot profiles can pass simultaneously;
- the swept polygon for the requested maneuver;
- which other swept polygons geometrically conflict;
- the time interval including braking and clock-skew buffers.

A large robot can therefore cause a junction or aisle to become exclusive without any hand-edited capacity number. If it cannot make a turn, the global route planner excludes that maneuver and returns a reason trace.

## 8. Robot runtime

Each robot namespace owns:

- `robot_state_publisher` with a unique `tf_prefix` / frame tree;
- Gazebo bridge for `/cmd_vel`, `/odom`, `/scan`, joint state, battery, and contacts as needed;
- localization (AMCL for map-based runs, or a clearly labeled ground-truth localization profile for early integration);
- Nav2 planner, controller, behavior server, smoother, navigator, and lifecycle manager;
- Nav2 Collision Monitor as the final deterministic velocity safety layer;
- `robot_agent_ros`, which owns task phase, candidate route choice, intents, bids, reservations, fairness, and degraded-mode policy;
- a health publisher with lifecycle and last-update timestamps.

The agent does not publish to the final wheel command topic. The command chain is:

```text
robot_agent_ros -> Nav2 action -> controller cmd_vel -> collision_monitor -> Gazebo drive plugin
```

Policy cancellation, pause, or emergency stop uses ROS actions/services and lifecycle state, not shared in-memory flags.

## 9. JEC and distributed coordination semantics

Each JEC is a ROS lifecycle node scoped to one or more junction resources. It owns only local state:

- approaching intents within its horizon;
- current and predicted occupancy;
- reservation leases for its jurisdiction;
- conflict cells and their membership;
- local fairness age and queue;
- blockage and health context relevant to its resources;
- a deterministic decision log.

It must not own global routes or call Nav2 actions.

### Degraded operation

If a JEC heartbeat/liveliness expires:

1. grants remain valid only until their signed/identified lease expiry;
2. robots already inside a conflict resource finish under local safety rules;
3. approaching robots stop before the commit line;
4. eligible robots form a scoped peer conflict group;
5. deterministic priority uses urgency, wait age, robot ID, and request sequence;
6. throughput may degrade, but unsafe entry is forbidden;
7. a restarted JEC enters `RECONCILING`, receives current robot intents/occupancy, then becomes `ACTIVE`.

This must be tested under transport impairment, clock progression, and process restart. A UI animation is not evidence.

- `OccupancyWindow.msg`
- `RobotIntent.msg`

- `ReservationDecision.msg`
- `JunctionState.msg`
- `ConflictCell.msg`
- `ContextEvent.msg`
- `TaskAnnouncement.msg`
- `TaskBid.msg`
- `TaskAward.msg`
- `DecisionTrace.msg`
- `SafetyEvent.msg`
- `SpawnRobot.srv`
- `InjectFailure.srv`
- `RunScenario.action`

Every coordination message requires:

- schema version;
- source ID and sequence number;
- ROS simulation timestamp;
- correlation / command ID where applicable;
- validity or lease expiry;
- frame ID for geometric data;
- explicit confidence only where it has defined semantics.

Define QoS intentionally:

| Data | Suggested QoS |
|---|---|
| pose / velocity / intent | best effort, keep last 1–5, deadline and lifespan |
| reservation decision | reliable, keep last, explicit lease and acknowledgment |
| context blockage event | reliable, transient local only if late joiners need current state |
| health / liveliness | reliable with liveliness and deadline |
| metrics / visualization | best effort; never backpressure motion |
| command result | reliable and idempotent by command ID |

Do not make JSON Schema the robotics source of truth. Generate or hand-maintain the web DTO schema at the gateway boundary, then enforce ROS-to-DTO contract tests. The currently empty schema files can become those external DTO contracts.

## 12. Real-time frontend architecture

Retain the current Next.js dashboard, but change its data contract.

### Gateway responsibilities

- subscribe to ROS telemetry and decision topics;
- normalize frames and units;
- maintain a bounded latest-state projection;
- publish snapshot + delta frames over WebSocket;
- accept idempotent operator commands and return asynchronous status;
- expose health, versions, scenario manifest, and data freshness;
- persist experiment metadata and operator audit events;
- never infer or advance robot motion.

### Browser responsibilities

- render static world geometry from the same generated map artifact;
- render robot footprint polygons based on profile dimensions;
- interpolate between timestamped backend poses only for visual smoothness;
- stop extrapolating and mark stale after a short freshness threshold;
- display connected/degraded/disconnected truth visibly;
- show command lifecycle and backend rejection reasons;
- show JEC jurisdictions, swept reservations, intent ribbons, and contact/safety events;
- use recorded playback through the same DTOs as live mode.

Target data rates:

- robot pose deltas: 10–20 Hz;
- intent / reservation state: 2–5 Hz plus event updates;
- aggregate metrics: 1 Hz;
- static map/profile/version data: once per connection or version change.

The browser may animate at 60 FPS, but it may not create new physical state.

### 12.1 No-static-frontend rules

The production frontend must not contain:

- autonomous `requestAnimationFrame` world stepping;
- random task, route, pose, battery, queue, or metric generation;
- hard-coded robot counts presented as current state;
- timers that increment completed tasks;
- fallback sample snapshots after connection failure;
- optimistic “robot spawned” or “failure injected” state before backend confirmation;
- direct imports of the coordination algorithm;
- controls that only change Zustand/React state;
- a hidden mock WebSocket server used by the normal launch command.

Fixtures are allowed only inside tests and Storybook-like isolated component previews. They must not be bundled into or reachable from the production live route.

### 12.2 Stream protocol

On connection, the gateway sends:

1. `hello`: protocol version, run ID, mode, ROS/Gazebo versions, world hash, server time;
2. `static_manifest`: map version, resource geometry, robot profiles;
3. `snapshot`: complete current state with monotonically increasing revision;
4. `delta`: ordered changes with base revision and source timestamps;
5. `event`: reservations, conflicts, task transitions, safety actions, contacts, command results;
6. `health`: component lifecycle and freshness.

If a delta is missed, the browser requests a new snapshot. It must not guess. After the freshness threshold, affected objects become stale and stop extrapolating.

### 12.3 Initial performance and fidelity budgets

These are release targets to validate on the selected demo machine, not claims about the current repository:

- pose publication: at least 10 Hz per robot;
- local UI state latency: p95 below 200 ms from ROS message timestamp to browser receipt;
- visual interpolation error at received sample timestamps: at most 5 cm against the projected ROS pose;
- stale warning: no later than 500 ms after expected pose updates stop;
- command acknowledgment: p95 below 250 ms locally;
- robot spawn reaches `READY`: target below 20 seconds after validation;
- browser renderer: 50+ FPS with ten robots on the demo machine;
- gateway restart: reconnect and authoritative resnapshot without affecting robot motion;
- bounded client memory during a 30-minute run.

If hardware cannot meet these budgets, record the measured limit and reduce visualization rate before weakening the robotics loop.

### 12.4 Required real-time proof

For an acceptance run, capture the same moment from:

- Gazebo GUI or server state;
- `ros2 topic echo` / action state;
- gateway WebSocket frame;
- browser render.

Robot ID, pose, timestamp, task, and navigation state must agree within declared tolerances. This four-way comparison is required evidence that the frontend is live rather than independently animated.

## 13. Failure lab with real effects

| Operator action | Required backend effect | Proof |
|---|---|---|
| Block aisle | Spawn a Gazebo obstacle or close a physical gate | sensor/costmap observation, context event, route change |
| Fail robot | stop/pause its control stack or deactivate drive | zero velocity, task lease expiry, reassignment |
| Kill JEC | terminate/deactivate the JEC node/process | liveliness loss, degraded protocol, continued safe progress |
| Network loss | `tc netem` on selected namespace/link, or labeled transport proxy | measured drop/latency and stale-message behavior |
| Battery critical | publish profile-consistent battery state | task policy change and navigation to charger |
| Demand surge | publish a reproducible task trace | increased queue, prediction, changed route decisions |
| Recover | restart and reconcile node/entity state | health transition and no duplicate ownership |

## 14. Observability and experiment evidence

Each run produces:

- immutable `run_manifest.json` with git SHA, image digest, ROS/Gazebo/Nav2/rmw versions, seed, mode, robot profiles, world hash, and scenario hash;
- rosbag2 MCAP containing the selected coordination, state, command, contact, and metrics topics;
- structured node logs with run and correlation IDs;
- result JSON/CSV derived from the bag or a deterministic metrics node;
- optional video/screenshot artifact for the named demo scenario;
- resource metrics per process/container.

Collision truth must use Gazebo contact data. Throughput, waiting, and travel metrics must use ROS timestamps and task state transitions. Network metrics must be measured at the ROS/transport boundary, not estimated from UI events.

## 16. Test pyramid

1. **Pure model tests:** routing, fairness, reservation overlap, deterministic arbitration, geometry predicates.
2. **ROS unit/component tests:** message validation, lifecycle transitions, QoS, lease expiry, idempotency.
3. **Launch tests:** one namespace, multiple namespaces, router and gateway loss, clean shutdown.
4. **Gazebo integration tests:** physical motion, sensing, footprint clearance, contact detection, dynamic spawn.
5. **Scenario tests:** narrow aisle, four-way junction, blockage, JEC failure, robot failure, network impairment, large robot.
6. **Web contract tests:** state freshness, reconnect, command lifecycle, no fabricated fallback state.
7. **Statistical experiments:** seeded mode comparisons and 100-scenario release campaign.

Fast Python DES tests remain useful at level 1. They do not satisfy levels 2–7.

## 19. Decisions versus open choices

### Recommended decisions to lock

- Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic.
- `rmw_zenoh_cpp` with documented router-assisted discovery; no routerless marketing claim.
- Nav2 per robot namespace and Nav2 Collision Monitor in the final velocity chain.
- Gazebo contacts as collision truth.
- One canonical robot profile drives physics, navigation, coordination, and UI.
- One canonical map source generates or validates all consumers.
- Existing Python DES remains a model harness, not the production runtime.
- Existing Next.js UI is retained and connected through a ROS telemetry gateway.

### Choices still needing an explicit project decision

- Target demo machine CPU, RAM, and GPU budget. This determines whether ten AMCL/LiDAR stacks and Gazebo GUI run together or use a headless server plus separate UI.
- Whether the release demo requires sensor-based AMCL for all ten robots or allows a labeled ground-truth localization profile while keeping Nav2 and physics real.
- Exact small and large AMR dimensions and payload/mass values.
- Whether dynamic robot placement is a live operator feature or a scenario-editor feature available only while paused.
- Whether the final physical-hardware target exists; if so, its drive, sensor, and safety interfaces must shape the adapter now.

These choices do not block Phase 0 or the one-robot vertical slice. Defaults can be used, but they must be marked as defaults rather than facts.
