# Code evidence review — SIH-123

Reviewed 2026-09-19 against `.unlazy/industry-plan/PLAN.md` and `gates/leaf-1.1.md`. This memo separates current source evidence from defects, placeholders, historical artifacts, and unverified live behavior. It assumes the agreed target: three people, simulation only, a 6–8 week working prototype, followed by a commercial warehouse-fleet path.

## Pass 1 — Implemented and reusable

The repository has a coherent algorithmic prototype that is worth preserving as the simulation reference.

- The graph model loads nodes, edges, aisle ownership, JEC coverage, capacities, widths and lane geometry (`robotics_ws/fleet_core/warehouse.py:85-140`, `:186-225`). A* and alternative-route generation are implemented (`robotics_ws/fleet_core/routing.py:43-113`). Social route scoring has explicit own-time, wait, congestion, externality, energy and risk terms (`robotics_ws/fleet_core/social.py:63-169`).
- Domain messages cover reservations, intents, TTL context events and tasks, with JSON round trips (`robotics_ws/fleet_core/types.py:41-164`). This is useful in-process vocabulary, but it is not yet an enforceable wire contract.
- The safety layer is pure and deterministic: separation with braking/staleness margin, capacity, narrow-gate direction, reservation ownership and short-horizon collision prediction (`robotics_ws/fleet_core/safety.py:1-13`, `:115-211`, `:250-280`). Robot movement invokes it before advancing (`robotics_ws/robot_agent/agent.py:945-991`).
- Robot agents publish heartbeats/intents, bid for tasks, request JEC/P2P resources, replan and execute graph-edge motion (`robotics_ws/robot_agent/agent.py:149-259`, `:493-557`, `:600-755`). The DES harness assembles the same agent classes with virtual time and impaired in-process transport (`robotics_ws/sim_runner/des_fleet.py:1-8`, `:157-233`).
- Zenoh/UDP/in-process transport abstractions include delayed delivery, loss, radio-range filtering and traffic counters (`robotics_ws/fleet_transport/base.py:89-168`; `robotics_ws/fleet_transport/zenoh_backend.py:22-81`). The JEC has local reservations, gate hysteresis, conflict cells and predictor inference (`robotics_ws/junction_edge_cell/jec.py:119-217`, `:264-309`, `:410-450`).
- The allocator has auction, deterministic tie-breaking, dock admission, failure requeue and scenario task generation (`robotics_ws/task_allocator/allocator.py:151-217`, `:226-249`). The bridge exposes REST/socket.io map, snapshot, metrics, experiment and control endpoints (`robotics_ws/telemetry_bridge/bridge.py:350-421`), and the UI renders map, robots, JECs, event/decision/failure/benchmark panels (`src/app/page.tsx:50-179`).

These capabilities support a narrow three-robot simulation demo after repair. They do not support the inherited ten-robot, ROS/Gazebo or physical-safety claims.

## Pass 2 — Defects and blockers

Ranked by risk to a truthful three-robot prototype.

1. **P0 — Energy and charger behavior is not safe enough for the acceptance gate.** Battery values are percentages in configuration and robot state (`configs/fleet_config.json:32-41`, `robotics_ws/robot_agent/agent.py:89-90`, `:307-323`), while the new plan requires a `0..1` SOC boundary and unknown/null semantics. More seriously, a robot in `TO_CHARGE` is excluded from the critical-battery abort branch (`agent.py:320-323`) and `_advance` has no zero-energy inhibition (`agent.py:945-991`), so a depleted robot can continue moving toward the charger. Charging admission only counts peer heartbeats already in `CHARGING` (`agent.py:786-797`); there is no charger reservation, lease, confirmed dock slot, or single-writer energy state. The canvas also treats battery as `0..1` (`src/features/fleet/warehouse-canvas.tsx:759-765`) while the backend sends `0..100`, so the visual low-battery arc never activates for normal percentage values. Normalize units, stop at zero, reserve a compatible charger, and add a direct energy/charging observer before claiming the scenario works.

2. **P0 — JEC leases can authorize conflicting physical entry.** On conflict the JEC preempts an existing grant by marking it expired before physical exit (`robotics_ws/junction_edge_cell/jec.py:136-168`). It also expires grants at `end + lease` without proving that the robot exited (`jec.py:248-262`). The implementation plan explicitly requires uncertain occupancy to remain held through partitions/restarts. For the prototype, remove preemption, retain occupancy until an observed exit/reconciliation, and make a missing reply or stale grant produce safe holding.

3. **P0 — Task/command truth is process-local and commands have no lifecycle.** Allocator tasks and counters live only in dictionaries/deques (`robotics_ws/task_allocator/allocator.py:36-47`); bridge state/events are also in memory (`robotics_ws/telemetry_bridge/bridge.py:70-83`). `POST /api/control` publishes a command and immediately returns `{ok:true}` without a command ID, accepted/rejected/pending/confirmed outcome, timeout or idempotency key (`bridge.py:372-383`). The failure UI records “sent” locally after this response (`src/features/failure-lab/index.tsx:89-95`). A restart therefore loses task/command truth and a retry can duplicate an action. Add a small durable simulation ledger and command envelope/outcome records before adding more scenarios.

4. **P0 — Stale state is removed instead of retained and marked stale.** The bridge deletes robots after heartbeat TTL and deletes their intents (`robotics_ws/telemetry_bridge/bridge.py:202-206`); only JECs are retained with `alive:false` (`:207-211`). This contradicts the planned operator behavior that identity and last-known values remain inspectable while actions are disabled. The UI only shows a generic “Backend Disconnected” overlay (`src/features/fleet/warehouse-canvas.tsx:173-177`) and labels disconnected state “Autonomous Sim” (`src/app/page.tsx:75-85`), which is ambiguous and conflicts with the required LIVE/REPLAY/OFFLINE model.

5. **P1 — Demand context is dead code.** In `_pool_drained`, `return` occurs before the `DEMAND_LEVEL` broadcast (`robotics_ws/task_allocator/allocator.py:126-140`). JEC demand features therefore do not receive the advertised schedule prior, making predictor inputs and “demand surge” behavior incomplete. Move the broadcast into the reachable tick path and add a test that the JEC feature changes.

6. **P1 — The protocol contract and adapters are placeholders.** All eight files under `contracts/` are zero bytes (`task.schema.json`, `robot_state.schema.json`, `robot_intent.schema.json`, `reservation.schema.json`, `event_envelope.schema.json`, `decision.schema.json`, `conflict.schema.json`, `jec_state.schema.json`). The only adapter is explicitly a mock: it teleports to the waypoint after a 100 ms sleep (`fleet/adapters/mock_adapter.py:6-24`). There is no ROS package, Gazebo world/model, Nav2 action, sensor/contact stream or real adapter, consistent with the gap review (`docs/ROS2_GAZEBO_PRODUCTION_PLAN.md:69-80`, `:89-101`). Keep this adapter isolated as a fixture; do not present it as motion integration.

7. **P1 — Map, launcher and control identifiers disagree.** The current map defines nine JECs (`configs/warehouse_map.json:168-177`), while `scripts/dev.sh` and the supervisor status text say six and the status/README repeat six. The supervisor loop actually iterates the map, so the displayed count is also misleading (`robotics_ws/supervisor/launch.py:127-141`). The Failure Lab offers `JEC-J19`, `JEC-J06`, and `JEC-J03` (`src/features/failure-lab/index.tsx:98-99`), but the map IDs are `JEC-01` through `JEC-09`; the documented/tested `JEC-04`/`JEC-01` identifiers are the valid ones (`robotics_ws/tests/test_integration.py:117-146`). A demo control can therefore return success without affecting a process. Generate choices from the snapshot/config and assert target existence.

8. **P1 — Existing integration tests contain weak or misleading assertions.** `test_conflict_cells_form_and_expire` includes the vacuous assertion `len(...) >= 0` (`robotics_ws/tests/test_integration.py:70-79`). The failure-reassignment test hard-codes `R03` when excluding the failed robot, even though the holder is selected dynamically (`:153-167`). The repository has 51 `test_*` functions by source count, while README claims 46 (`README.md:116-125`). The tests were not rerun here because this host has no `python` or `python3` executable; the attempted `python -m pytest robotics_ws/tests -q` failed before collection. Treat the claimed “46/46” as historical until a pinned runtime reruns them.

## Pass 3 — Placeholders, historical claims and unverified behavior

- `IMPLEMENTATION_STATUS.md` marks ten AMRs, six JECs, battery behavior, JEC failover, predictor quality, live UI, benchmarks, persistence, 46/46 tests and clean setup as complete (`IMPLEMENTATION_STATUS.md:41-80`). Source review only verifies that corresponding code paths exist; it does not verify the live claims. The current gap review correctly classifies the repository as a graph/point-mass prototype and lists ROS/Gazebo, physics, contracts, adapters and safety evidence as absent (`docs/ROS2_GAZEBO_PRODUCTION_PLAN.md:57-101`).
- `docs/EXPERIMENTS.md` calls its table “current results” and says all values come from `results/latest.json` (`docs/EXPERIMENTS.md:27-38`, `:65-67`), but the stored `results/latest.json` points to `/home/z/my-project/...` and includes nonzero collision counts, including a full-mode aggregate of 1.4. Those are historical simulator artifacts, not current zero-collision evidence. The same document describes network/JEC/robot chaos as measured (`:40-48`); no current live run was possible on this host.
- The predictor implementation is real numpy inference with a temporal split (`robotics_ws/congestion_predictor/train.py:98-130`), but its dataset is generated by the same custom simulator and the stored score is historical model evidence. It does not establish downstream completion-time benefit or physical safety. The production plan correctly says to rebuild scenario-separated datasets and keep the MLP experimental (`docs/IMPLEMENTATION_PLAN.md:211-217`).
- The UI is a useful telemetry surface, but its “live”/“autonomous sim” wording and Failure Lab controls can imply a running authoritative backend when disconnected (`src/app/page.tsx:75-85`, `src/features/failure-lab/index.tsx:108-110`). No authenticated command boundary, replay mode, or browser-to-backend command acknowledgement is implemented in the inspected path.
- `prisma/schema.prisma` is the generic User/Post starter (`prisma/schema.prisma:7-30`), and no robotics code imports `src/lib/db.ts` for task, event, robot or command persistence. The `results/` files are run exports, not durable operational state.

## Pass 4 — Ranked reuse and correction plan for three people

1. **First integration gate (A/B/C, 1–2 days):** reduce the default scenario/config to exactly three declared robots; generate JEC/resource IDs from the map; add a truthful launcher health check; freeze units (`SOC 0..1`, metres, seconds) and a versioned JSON contract. Keep the DES runtime and current graph map as the fast reference.
2. **Coordination/backend owner (B, days 2–7):** repair JEC arbitration so grants are never preempted or expired solely by time; add resource/request IDs, observed-exit release, charger occupancy, zero-energy stop, task custody and a durable event/command ledger. Return command IDs and explicit pending/confirmed/rejected/unknown outcomes. Fix demand context and make failed/reconnected commands idempotent.
3. **Runtime/safety owner (A, days 2–10):** add an independent geometry observer over simulator truth, finite three-robot workloads, initial SOC/charger contention fixtures, and preserved failed/unfinished runs. Validate zero overlap for declared seeds, blocked-route behavior, depleted stop, and no dual charger occupancy. This observer must be separate from robot telemetry.
4. **UI/integration owner (C, days 2–10):** consume the real snapshot/task ledger, retain stale robots with age/reason, display LIVE/REPLAY/OFFLINE explicitly, disable incompatible controls, show command outcomes, fix battery normalization, and derive Failure Lab resource/robot choices from current state. Add a two-browser/reconnect smoke check.
5. **Benchmark gate (days 10–15):** use a finite batch and make completion time/makespan primary; report unfinished work, flow time, intervention, charging wait, energy and safety events. Compare stop-and-wait, reactive, peer-only and optional JEC modes with the same seeds and geometry. Treat `results/` as evidence only when a run manifest links code/config/map/seed/trace and the run was reproduced on the current environment.
6. **Commercial path (after the simulation gate):** preserve the current agents and DES tests behind explicit ports, then add ROS 2/Gazebo/Nav2 packages, real robot profiles/footprints, sensor and contact truth, adapter/action correlation, restart reconciliation, and deployment/CI. The mock adapter and current point-mass movement are acceptable fixtures for the prototype, not product completion evidence.
